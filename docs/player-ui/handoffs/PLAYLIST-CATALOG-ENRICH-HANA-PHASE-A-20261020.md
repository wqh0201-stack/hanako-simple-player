## A1. 生产闸门与可取消冷却

`netease-gate.js` 当前 schedule() 不接 signal，cool() 后排队任务直接在后端等待60秒，停止后仍可能到点继续外发；尚未提供前端可读的结构化冷却状态。

要求：

- 全实例同源请求起始至少2000ms，重试/回退也经过闸门；原请求缓存命中不白等。
- 405/429后60秒保护期间不能因后续曲目/多窗口继续发；明确当前冷却、剩余时间和上游码/阶段，便于前端一次恢复试探而不是堆排队任务。
- 信号/取消应清理等待与队列；取消等待及时返回，不能到点才补发已取消请求。底层路由实际能传播到何处需核对官方契约并如实报告，不能用假宿主测过宣称真宿主取消已验证。
- 不将所有普通404当限流；业务405与HTTP405区分。不得把“未再即时重试”冒充已经完成全局保护。
- 注入时钟/睡眠做测试，**生产默认2000/60000不改成0来验闸门**。现有查询语义测试可继续注入0，但必须另有非零真实规则的时序测试。

## A2. 持久索引的断点/分页/拒绝保护

`catalog-index.js` 当前：

- listAlbums 固定最多两页；more=true结果标fresh30天后，下次仍只返回这两页，没有向后续页继续的游标。
- 第二页错误全部吞成warn，包括405；build又逐张catch继续。这样可能把拒绝后的等待/连败藏进同一个长请求，前端无从暂停与有界恢复。
- 注释说每张专辑独立落盘，但实际仅在整批循环结束后save，save又是120ms延迟；中断时未必保住已经完成的关系。
- artist每次先查通用请求缓存，没有优先复用持久artist关系。

要求：

- 保存分页进度与覆盖状态，有限分批向后继续；more=true不得作缺失归属否定，也不能永远停留第一页/两页。失败保留成功部分，不清索引。
- 每张成功专辑的可恢复关系可靠落盘。复用旧v2请求缓存缺少新字段时，以详情补齐pic/type/发行信息，不能存在tracks但cover因为meta.pic缺失失败。
- 拒绝/冷却及时返回结构化暂停状态，停止本批后续外发，别在build内部悄悄等60秒再反复打8张。前端稍后承担暂停/一次恢复策略。
- 有效持久artist/index命中可以不依赖400条通用缓存；复用/过期/增量/中断恢复要有可计数证据。

## A3. 图片与歌词缓存的确实一次复用

当前 cover()/lyric() 没有在途合并；并发缓存未命中可重复下载同一图片/歌词。每图有8MiB上限但没有总体容量边界；cover类型只验image/，缓存后靠扩展名猜类型；lyric仅在getLyric外schedule一次，内部多个Meting节点回退未必都经过闸门。

要求：

- 同缓存键并发 single-flight；成功落盘后跨实例重建可复用，同album+源图变化生成新键。缓存命中0外发，错误不缓存成空成功，临时文件不作为命中。
- 严格id/路径/官方图床；只接受明确安全图片类型及合理字节，保存/读取Content-Type一致。总体容量有界，清理仅自身缓存文件，不动用户文件。
- 同provider/songId歌词缓存独立，保留用户旧LRC；空白/纯音乐占位/非法响应不得冒充成功。供整理使用的每一次真实回退/重试也经过共享调度，不为此改变无关播放路径。
- 准确区分无歌词与网络错误，给后续前端可用状态。

## Hana 对 1003131787 的独立实测：4 个实际失败，不只是缺测试

直接导入当前生产模块，用注入时钟与临时 dataDir，无真实网络、无用户数据写入，临时目录已清理。

### F1 并发闸门漏放

三个并发 `await gate.schedule()`；注入时钟从0推进到2000，并同时释放两个等待项：

```json
{"starts":[{"id":0,"at":0},{"id":1,"at":2000},{"id":2,"at":2000}],"violation":true}
```

第三个请求应该不早于4000，却与第二个同为2000。原因是 `gatePromise` 创建时立刻 `run()`，而不是等上一项 tail 后再执行；等间隔的多个等待者同时醒来，未重新串行校验 nextAt。把结果 Promise 接到 tail 并没有串行化真实闸门执行。

修复并加入**3个以上并发**的时序断言，不只串行调两次。取消/冷却不能引入未处理拒绝或迟到补发。

### F2 歌词节点回退绕过闸门

隔离 ctx.network.fetch 第一次返回 HTTP503，第二次返回有效LRC；spy gate统计：

```json
{"fetches":2,"schedules":1,"everyAttemptGated":false,"returned":true}
```

即 getLyric 内部下一节点发生真实请求却未schedule。整理取词的每次回退/重试都须过同一个闸门，不能只在getLyric外包一次；不要因此改坏无关播放/搜索行为。

### F3 songId 非法字符串被静默接受

`catalogIndex.lyric('abc456def')` 当前返回成功，自动把输入洗成456。API参数应严格验证而非抽数字，需返回400且不发网、不写缓存。其他artistId/albumId入口同样检查。

### F4 上游 JSON 错误被当歌词成功落盘

隔离网络返回 HTTP200、text为 `{"code":405,"message":"refused"}`，调用 `lyric('789')`：

```json
{"jsonAcceptedAsSuccess":true,"persisted":true}
```

当前返回该JSON文本且写入 `catalog-lyrics/789.lrc`。这会把失败永久伪装成歌词缓存命中。必须识别 JSON/HTML错误与可用歌词，保留业务码/阶段，405/429按保护处理；无词占位与网络错误分开，不写坏成功缓存。

### 现有验证脚本的假设需同步修正

`verify-phase-a.mjs` 的分页 mock 用 `pages[offset]`，第一页返回2项、nextOffset=2时直接跳到array索引2（第三页），不是真正验证第二页/第三页。请改为明确的 offset→page 映射（例如0、2、3），断言完整 more=false、所有ID都在且每页只读一次，模块重建不重复已完成项。

容量清理目前挑选任何非meta/non-tmp文件，必须限制为自己生成的严格命名缓存，不能把该目录中无关文件/目录/符号链接当可删缓存。参数拒绝、MIME/容量/冷却等路由集成可复用现有 `verify-backend.mjs` 的捕获路由处理器模式，**不安装新框架、不跑整套旧测试**。
