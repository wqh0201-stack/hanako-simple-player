## 2. 宿主契约（权威口径）

来源：`~/.hanako/artifacts/server/1.1.0-beta-darwin-arm64-ddbcc90ee2fc26ef-ge9e41495f3d78133/APPS.md`「卡片尺寸与形态契约」「尺寸信封（`hana.envelope`）」。

**三层尺寸模型**：① 声明式初始占位（`aspectRatio`）→ ② 运行时报高（页面 `hana.ui.resize({width?,height?})`）→ ③ 宿主兜底与最终裁决（clamp 后落框，聊天流高度上限为聊天可视区换算 cap）。

**各挂载位模式**：

| 挂载位 | 高度模式 | 备注 |
|---|---|---|
| 聊天流插件卡 | `flexible` | 上限为聊天可视区换算 cap |
| 黑板 / 拆窗 | `fixed` | 用户拖拽的容器优先，内容上报不采纳 |
| page / widget | 高 `flexible` | 宽由容器锁死 |
| 槽位 iframe | `fixed` 160 | 宿主定档，贡献方不能上报 resize |
| App 输入面板 | `fixed` | 宿主分配有限容器，页面内部滚动 |

**信封（只读信号）实际推送值**：

| 挂载位 | height | width |
|---|---|---|
| 聊天流插件卡 | `flexible`，`max` = 聊天可视区高度上限 | `flexible`，`max` = 卡壳 `clientWidth` |
| 黑板 / 拆窗 | `fixed`，容器 `clientHeight` | `fixed`，容器 `clientWidth` |
| page / widget | `flexible`，视口高减宿主标题栏余量 | `fixed`，容器 `clientWidth` |

页面侧官方 API：`hana.envelope.getSnapshot()` / `.subscribe()`（iframe `ready` 时发一次快照，之后只在实质变化时重发）。本项目 `ui/app.js` 已有订阅（歌词面恢复用），**横条应复用这条通道，不要自建轮询**。

**结论**：契约里**没有**任何「横条 / 顶部条」专用槽位；也没有最小宽高承诺。宽而矮的预算完全由宿主分配结果决定。

## 3. 宿主渲染器里的实际几何（安全区）

来源：`desktop/dist-renderer/assets/ChatTranscript-*.css`、`CardShell-*.css/js`、`styles.css`（宿主自带产物，非本项目代码）。

```
:root {
  --panel-edge-gap: 6px;            /* styles.css */
  --card-top-inset: var(--panel-edge-gap);   /* 6px */
  --card-top-btn-size: 24px;
  --card-top-btn-pad: 2px;
  --card-top-btn-hover-inset: 3px;
  --card-top-island-inset: calc(var(--card-top-inset) - var(--card-top-btn-pad));
}
```

- 单枚宿主控件按钮 = `24 + 2×2 = 28px`；CardShell 里另有一处 `s*2 + r`（inset×2 + 按钮尺寸）= **36px**，即宿主给自己控件预留的**顶带高度**。
- 拆窗（detached）壳另用 `--card-top-inset: 8px`，比聊天卡更松。
- 移动端 `--card-top-btn-size: 30px`（不属本轮桌面验收范围）。
- 因此项目沿用的 **「聊天卡右上 100×40 不放文字/控件」** 是**保守且仍然成立**的约定：高度 40 已覆盖宿主约 36px 的顶带；宽度 100 ≈ 3 枚按钮 + 间隙。

**对横条的直接含义**：横条越矮，右上这块占比越大。当前实现把条放在 `top: max(40px, (100%-64px)/2)`、右缘留 12px，即整条压在 40px 安全带**下方**——方向正确；但 104px 高的最小态下，条高 64 + 上边 40 = 104，**一点余量都没有**，需要真机确认宿主控件岛不会压到条顶边（见 §7）。

## 4. 公开工具能读到什么

- **没有**「读某张卡 iframe 像素尺寸」的公开工具（`tool_search` 确认；`ui_inspect` 只给实例/就绪/placement，不给像素）。
- **可以**：`ui_action` 的 `describe_dom` / `describe_elements` 返回卡内元素的 **CSS px 边界**（`bounds: {x,y,width,height}`），坐标是卡内坐标系。若被测元素铺满视口（如 App 根 `.frame`/`.player`），其边界即 **iframe 内容盒尺寸**——这是外部唯一可用的「实际尺寸」读法。
- **实测样本（本次真机）**：当前窗口里一张聊天流内的交互卡，根元素 `div#box.ac` = **483×316 CSS px**（x=0,y=0），与其内部元素自洽；说明该读法可用、数值可信。注意这是 `show_card` 交互卡，v2 插件卡的卡壳内边距可能略有差异，量横条时请以**横条卡自己**的根元素为准。
- 页面内可直接用 `hana.envelope` 与 `getBoundingClientRect()`；`ui_action describe_dom` 用于**外部**取证，两者应交叉一致。

## 5. 用户截图测量（旧 build，非横条实现）

用户提供的两张截图来自**已安装的旧 build `1003131710`**（当时横条尚未实现），用于说明「现在最小态已经崩了」。

| 图 | 截图尺寸 | 场景 |
|---|---|---|
| A | 1402×122 | 宽态（长边可继续拉长，只受显示器限制） |
| B | 492×122 | 最小态（用户明确：横向与纵向都是最小） |

**比例推导**：截图中播放键是纯色圆盘，量得直径 **52 截图像素**；项目 CSS 中 `.controls .play-btn` 恒为 **44px**（无任何布局覆盖），故比例 ≈ **52/44 = 1.18 截图px/CSS px**。两张图比例一致（同一元素同样 52px）。

换算（≈，带 ±2% 误差）：

| 图 | 截图px | ≈ CSS px |
|---|---|---|
| A 宽态 | 1402×122 | ≈ 1186×103 |
| B 最小态 | 492×122 | ≈ **416×103** |

**旧 build 在最小态的实际表现**（截图观察，供对照）：控件被卡片下沿裁切、时间被挤到身份区后面、队列入口压到宿主关闭键上、身份文案丢失——即任务要解决的现象。

**用户对设计目标的原话修正**：

- 「宽度没有上限，长边可以更长，只取决于显示器长度。」
- 「高度没有上限，可以铺满整个窗口。」
- 「建议设计目标按这个（1402 宽态）再窄一半也兼容」——即约 **701 截图像素 ≈ 593 CSS px** 仍须完整可用。
- 结合最小态实测 **≈416 CSS px**，**真正的约束是 416 这一档**（593 已在其内）。当前实现自测覆盖到 312，比 416 更保守，是好事，不应缩小覆盖范围。

## 6. 给实现的具体建议

1. **别找「横条挂载位」**：横条 = 聊天流插件卡（或拆窗）在低高度预算下的第四态，靠可用宽高自决，不要试图申请专用槽位。
2. **尺寸来源只用两处**：页面内 `hana.envelope` + 容器 `ResizeObserver`；不要读宿主私有变量、不要自建轮询。
3. **最小宽度按 ≤416 CSS px 设计并留余量**（现实现 312 起步即可），封面 64×64 与身份区固定宽度不缩，靠弹性区与次级操作组退让。
4. **右上安全区照旧守 100×40**：横条越矮越要守；条顶边贴着 40px 线时，确认宿主控件岛（约 36px 高）不会与条重叠。
5. **宽度不必为「最宽」优化**：长边可到显示器宽度，只需保证不横向溢出、进度色场不重采样。
6. **高度不设上限**：竖高卡仍走既有 wide/long/compact，横条只在低高度区间触发（现实现 STRIP_IN 192 / STRIP_OUT 224 滞回）。
